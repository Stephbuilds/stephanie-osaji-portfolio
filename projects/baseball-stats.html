Baseball Stats + AI Player Bios

A data product built around a live third-party API: fully sortable and editable stats persisted to a local database, a derived metric shipped as a follow-on feature request, and an on-demand LLM-generated player bio, plus an incident diagnosed and resolved during development.

Node.js Express SQLite Google Gemini API Vanilla JS

The problem

Take a public, third-party baseball statistics API and turn it into a product: something a user can sort, edit, and trust as a source of truth, not just a static table dump, and then layer in an AI capability that adds genuine value without exceeding free-tier API limits.

Key decisions

Local database as source of truth, seeded once

The app fetches the source API exactly once, on first run, and never again. All reads and edits after that hit the local SQLite database. This was a deliberate choice: it means user edits persist across restarts and are never silently overwritten by a re-fetch. I verified this by editing a stat, restarting the server, and confirming the edit survived.

Handled messy source data instead of assuming it was clean

Inspecting the live API turned up inconsistent field names (one field literally called "third baseman" actually held triples) and no unique identifier, with two duplicate player names among 172 records. Rather than build on top of that, I mapped raw fields to sane column names, synthesized a primary key, and relabeled everything for display while preserving the original data underneath.

Cost-aware AI integration: cache, don't regenerate

The player bio feature calls an LLM, and free-tier LLM APIs are rate-limited. Instead of generating a bio on every click, the first generation is cached in the database. Later views are instant (~20ms) and cost nothing, with a manual "Regenerate" option for when a bio needs refreshing after a stat edit.

Shipped a follow-on feature without a database migration

When asked to add a "Hits Per Game" column after launch, I computed it client-side from existing Hits and Games fields rather than storing it. That way, it stays correct even if those underlying stats are edited later, with zero schema changes required.

The incident: a misleading quota error

After wiring up the Gemini integration and adding an API key, the first request failed with "Quota exceeded... limit: 0." That read like an account or billing problem, and my first hypothesis was exactly that. Instead of guessing further, I queried Gemini's live model list directly with the same key. The model I'd used (gemini-2.0-flash) was still listed, but a direct test against the newer gemini-2.5-flash came back with a much clearer signal: "no longer available to new users."

The root cause was that the account was provisioned on a newer model generation than the one I'd hardcoded. The fix wasn't just swapping in a working model name. It was switching to gemini-flash-latest, an alias Google maintains to always point at the current default model, so the same failure mode can't silently recur the next time a model gets deprecated. I verified the fix by generating a bio end-to-end and confirming the cache worked.
